# میدان — هسته بک‌اند پروژه (Laravel 11)

این پوشه شامل هسته اصلی پروژه‌ست: دیتابیس، مدل‌ها، سرویس‌ها و کنترلرهای هر سه پنل
(مشتری / غرفه‌دار / ادمین) به همراه اتصال کامل به درگاه **زرین‌پال**.

## نصب اولیه

✅ این نسخه دیگه فقط فایل‌های اختصاصی نیست — یک پروژه‌ی کامل و اجراپذیر Laravel 11
هست. تمام فایل‌های اسکلت (`artisan`, `public/index.php`, `bootstrap/`, همه‌ی
`config/*.php`) اضافه شده و `vendor/` هم از قبل نصب شده. `.env` هم روی
**SQLite + file cache/session + sync queue** تنظیم شده تا بدون نصب MySQL یا
Redis هم بالا بیاد. یعنی فقط PHP و Composer لازم دارید:

```bash
cd meydan
composer install          # اگه فولدر vendor به هر دلیلی نبود/ناقص بود

php artisan migrate
php artisan db:seed          # می‌سازد: admin@meydan.test / password
php artisan storage:link
php artisan serve
```

بعدش سایت روی `http://127.0.0.1:8000` بالاست. `APP_KEY` هم از قبل تو `.env`
ست شده، نیازی به `key:generate` نیست (اگه خواستید عوضش کنید، `php artisan
key:generate` رو بزنید).

> اگه ترجیح می‌دید از MySQL/Redis واقعی استفاده کنید (مثلاً برای دیپلوی
> نهایی روی سرور)، خطوط مربوطه که به‌صورت کامنت بالای `.env` گذاشته شده رو
> باز کنید و `DB_CONNECTION`, `QUEUE_CONNECTION`, `CACHE_STORE`,
> `SESSION_DRIVER` رو به `mysql` / `redis` تغییر بدید.

## ورود اولیه

بعد از `db:seed`، با این مشخصات وارد پنل ادمین بشوید و حتماً رمز را عوض کنید:
```
ایمیل: admin@meydan.test
رمز:   password
```

## احراز هویت و ثبت‌نام (تازه اضافه شد)

سیستم لاگین/ثبت‌نام به‌صورت دستی (بدون نیاز به Breeze) پیاده‌سازی شده، چون
دو نوع ثبت‌نام متفاوت لازم بود:

- **`/register`** — ثبت‌نام مشتری عادی (ساده: نام، موبایل، ایمیل، رمز).
- **`/register/vendor`** — ثبت‌نام غرفه‌دار: هم‌زمان یک حساب کاربری با نقش
  `vendor` و یک رکورد `Booth` با وضعیت `pending` می‌سازد. غرفه‌دار باید
  دسته‌بندی(ها)، اطلاعات تماس، کد ملی/شناسه ملی، و یک **مدرک هویتی یا جواز کسب**
  (الزامی) آپلود کند. این مدرک در دیسک `local` (خصوصی، غیرقابل‌دسترس عمومی) ذخیره
  می‌شود — یعنی فقط از طریق پنل ادمین قابل بازبینی است، نه لینک مستقیم در سایت.
- بعد از ثبت‌نام غرفه‌دار، کاربر به `vendor.pending` هدایت می‌شود و تا وقتی
  ادمین از پنل «تأیید» نزند، به داشبورد غرفه‌دار دسترسی ندارد
  (این منطق در `EnsureUserHasRole` میدل‌ور پیاده شده).
- بعد از لاگین، هر کاربر بر اساس نقشش خودکار به پنل درست هدایت می‌شود
  (`AuthenticatedSessionController::redirectPathForRole`).

> فراموش کردن رمز عبور و تأیید ایمیل هنوز اضافه نشده — اگر لازم دارید،
> ساده‌ترین راه نصب `laravel/breeze` و ادغام فقط همون دو بخش با کدهای فوقه.


## فعال‌سازی زرین‌پال — تنها کاری که باید بکنید

فقط این سه خط رو تو فایل `.env` پر کنید:

```
ZARINPAL_MERCHANT_ID=کد-مرچنت-شما
ZARINPAL_SANDBOX=false     # برای تست: true بگذارید
ZARINPAL_CALLBACK_URL="${APP_URL}/checkout/callback"
```

همین. به هیچ فایل دیگه‌ای نیازی نیست دست بزنید. کد `ZarinPalService.php`
هم درخواست پرداخت (`payment/request.json`) و هم تأیید تراکنش (`payment/verify.json`)
رو با API نسخه ۴ زرین‌پال کامل پیاده‌سازی کرده.

## جریان پرداخت (خلاصه)

1. مشتری از سبد خرید وارد `checkout.show` می‌شود و آدرس را انتخاب می‌کند.
2. با زدن دکمه پرداخت، `CheckoutController::pay` سفارش را می‌سازد
   (`OrderService::createFromCart`) — که خودش آیتم‌ها را بر اساس غرفه از هم جدا
   کرده و کمیسیون هر غرفه را طبق `commission_percent` محاسبه می‌کند.
3. کاربر به درگاه زرین‌پال ریدایرکت می‌شود.
4. بعد از پرداخت، زرین‌پال کاربر را به `checkout.callback` برمی‌گرداند.
5. `verifyPayment` تراکنش را تأیید می‌کند؛ در صورت موفقیت،
   `OrderService::markOrderPaid` سفارش را «پرداخت‌شده» می‌کند و برای هر غرفه‌ی
   درگیر در سفارش، یک `Shipment` (مرسوله) جدا می‌سازد — چون هر غرفه جدا ارسال می‌کند.

## مدل مالی و تسویه‌حساب

- پول مستقیم به حساب زرین‌پال **شما** (هلدینگ) واریز می‌شود، نه غرفه‌دار.
- `SettlementService::generateForAllBooths()` (قابل زمان‌بندی با Task Scheduler
  برای مثلاً هر ۱۵ روز یک‌بار) آیتم‌های سفارشِ پرداخت‌شده‌ی هر غرفه را جمع می‌زند
  و یک رکورد `Settlement` با مبلغ نهایی قابل واریز می‌سازد.
- ادمین از پنل، بعد از واریز دستی/بانکی، دکمه «تأیید واریز» را می‌زند
  (`SettlementController::markPaid`) و شماره پیگیری بانکی ثبت می‌شود.

> برای خودکارسازی کامل واریز (بدون دخالت دستی ادمین)، در آینده می‌توانید از
> قابلیت **تسهیم پرداخت (Split Payment)** زرین‌پال استفاده کنید که پول را
> مستقیم بین حساب هلدینگ و غرفه‌دار به‌نسبت درصد تقسیم می‌کند.

## فعال‌سازی پیامک (کاوه‌نگار) — تنها کاری که باید بکنید

```
KAVENEGAR_API_KEY=کد-اختصاصی-شما
KAVENEGAR_SENDER=              # خالی بگذارید تا از خط پیش‌فرض حساب استفاده شود
```

**نکته مهم:** پیامک‌های این پروژه همه از نوع «ارسال با الگو» (Verify Lookup)
هستن، نه پیامک آزاد — چون سریع‌تر تحویل داده می‌شن و نیاز به تأیید سرشماره
تبلیغاتی ندارن. یعنی قبل از اینکه پیامک‌ها واقعاً کار کنن، باید ۷ تا الگو رو
از پنل کاوه‌نگار (بخش «ارسال با الگو») با همون اسم‌هایی که تو `config/kavenegar.php`
نوشته شده بسازید و برای خط‌تون تأیید بگیرید. متن پیشنهادی هر الگو هم بالای
همون فایل کامنت شده — فقط کپی/پیست کنید.

**کجاها پیامک می‌ره (خودکار):**

| رویداد | گیرنده | فایل |
|---|---|---|
| ثبت‌نام (کد تأیید موبایل) | مشتری/غرفه‌دار جدید | `RegisteredUserController`, `VendorRegistrationController` |
| پرداخت موفق سفارش | مشتری | `OrderService::markOrderPaid` |
| سفارش جدید ثبت شد | غرفه‌دار (هرکدوم که تو سفارش سهم داشته) | `OrderService::markOrderPaid` |
| کد رهگیری پستی ثبت شد | مشتری | `Vendor\OrderController::markShipped` |
| تأیید غرفه | غرفه‌دار | `Admin\BoothController::approve` |
| رد غرفه (+ دلیل) | غرفه‌دار | `Admin\BoothController::reject` |
| واریز تسویه‌حساب | غرفه‌دار | `Admin\SettlementController::markPaid` |

اگر `KAVENEGAR_API_KEY` خالی باشد، پیامک‌ها ارسال نمی‌شن ولی سایت خطا نمی‌ده —
فقط یک لاگ هشدار (`Log::warning`) ثبت می‌شه، تا موقع توسعه/تست مزاحم کار نشه.

**تأیید شماره موبایل (OTP):** بعد از هر ثبت‌نام (چه مشتری چه غرفه‌دار)، کاربر
لاگین می‌شه ولی به `verify-phone` هدایت می‌شه تا کد ۵ رقمی پیامکی رو وارد کنه.
این کار برای یک سایت سراسری که هرکسی از هر جای ایران می‌تونه ثبت‌نام کنه، جلوی
ثبت‌نام با شماره جعلی/تکراری رو می‌گیره. کدها ۲ دقیقه اعتبار دارن و حداکثر
۵ بار تلاش اشتباه مجازه (جدول `otp_codes`).

**ورود با کد پیامکی (بدون رمز عبور):** جدا از لاگین معمولی با ایمیل/رمز، یک
مسیر `/login/otp` هم هست — کاربر فقط شماره موبایلش رو وارد می‌کنه، کد ۵ رقمی
می‌گیره، و بدون نیاز به رمز عبور وارد می‌شه. این برای کاربرانی که رمزشون یادشون
رفته یا اصلاً ترجیح می‌دن با موبایل وارد بشن (که تو ایران خیلی رایجه) طراحی شده.
لینکش زیر فرم لاگین معمولی هم هست. توجه: این فقط برای کسانی کار می‌کنه که قبلاً
حساب دارن — برای کاربر جدید همچنان باید از `/register` یا `/register/vendor`
استفاده کنه.

## حمل‌ونقل سراسری

چون سایت قراره در کل ایران استفاده بشه و هر غرفه ممکنه تو هر استانی باشه،
هزینه ارسال یک عدد ثابت نیست — `ShippingService` بر اساس فاصله‌ی مبدأ (غرفه)
تا مقصد (آدرس مشتری) و وزن کل سفارش محاسبه می‌کنه:

| منطقه | مصداق | هزینه پایه (تا ۱ کیلو) | هر کیلوی اضافه | زمان تقریبی |
|---|---|---|---|---|
| `same_city` | غرفه و مشتری هم‌شهر | ۲۵,۰۰۰ تومان | ۸,۰۰۰ تومان | همان روز تا ۱ روز |
| `same_province` | هم‌استان، شهر متفاوت | ۴۰,۰۰۰ تومان | ۱۵,۰۰۰ تومان | ۱ تا ۲ روز |
| `nationwide` | استان‌های دیگر | ۶۰,۰۰۰ تومان | ۲۵,۰۰۰ تومان | ۲ تا ۵ روز |

نکات مهم دربارهٔ این پیاده‌سازی:

- **هر غرفه، مرسوله و هزینه ارسال جدا داره.** اگر سفارش شامل محصولات از ۳ غرفه
  در ۳ استان مختلف باشه، مشتری ۳ هزینه ارسال جدا (که جمعشون تو صورت‌حساب
  می‌آد) و ۳ کد رهگیری جدا می‌بینه — چون هر غرفه مستقل بسته‌بندی و ارسال می‌کنه.
- وزن هر محصول موقع ثبت توسط غرفه‌دار وارد می‌شه (`weight_grams`)، پیش‌فرض ۵۰۰ گرم.
- نرخ‌ها فرضی‌اند. وقتی قرارداد واقعی با پست/تیپاکس/باربری بستید، فقط ثابت‌های
  بالای `ShippingService` رو عوض کنید — بقیه کد دست نمی‌خوره.
- **محدودیت شناخته‌شده:** دسته «املاک و ساخت‌وساز» چون کالای فیزیکی حمل‌شده
  نیست (زمین/ویلا)، منطقاً نباید وارد جریان «ارسال» بشه. فعلاً از نظر فنی این
  دسته هم مثل بقیه یک Shipment می‌سازه (با وزن حداقلی) که فقط برای جلوگیری از
  خطا هست — پیشنهاد می‌شه بعداً یک فلگ `is_shippable` روی دسته‌بندی اضافه کنید
  تا برای این‌جور دسته‌ها اصلاً مرحله «ارسال» و هزینه‌ی مرتبط باهاش نمایش داده نشه
  و به‌جاش مثلاً «هماهنگی حضوری» پیشنهاد بشه.

## حس SPA بدون بازنویسی به Vue/React (Turbo)

چون همه صفحات با Blade و رندر سمت سرور نوشته شده (که برای سئو بهترین گزینه‌ست)،
ولی می‌خواستید ناوبری‌اش شبیه یه اپ تک‌صفحه‌ای (SPA) باشه، از
**[Turbo](https://turbo.hotwired.dev)** استفاده شده — یه کتابخونه ~۱۵ کیلوبایتی
که فقط با یه خط `<script>` از CDN اضافه می‌شه (تو `layouts/app.blade.php` و
`layouts/panel.blade.php`، از قبل هست، نیازی به نصب npm/build نداره):

- کلیک رو هر لینک یا ارسال هر فرم، به‌جای رفرش کامل صفحه (فلاش سفید مرورگر)،
  فقط با AJAX محتوا رو عوض می‌کنه — دقیقاً حس یه SPA.
- یه نوار پیشرفت بالای صفحه موقع ناوبری نشون می‌ده (رنگش هم با برند هماهنگ شده).
- ناوبری‌های بعدی (وقتی کاربر رو یه صفحه دیده) سریع‌تر می‌شن چون Turbo از قبل
  کش می‌کنه.
- هیچ‌کدوم از منطق فعلی (فرم‌ها، اعتبارسنجی Laravel، فلش مسیج‌ها، JS داخل هر
  صفحه مثل جداکننده قیمت) نیازی به تغییر نداشت — Turbo روی هرچی که از قبل بود
  خودش رو تطبیق داد.

**یه نکته امنیتی/فنی مهم که رعایت شده:** فرم پرداخت زرین‌پال (`checkout.pay`)
چون کاربر رو به یه دامنه دیگه (زرین‌پال) ریدایرکت می‌کنه، با `data-turbo="false"`
از این رفتار مستثنی شده — وگرنه Turbo سعی می‌کرد صفحه زرین‌پال رو با fetch بگیره
و به‌جای رفتن واقعی به اون دامنه، محتواش رو جای صفحه فعلی بذاره، که کل جریان
پرداخت رو خراب می‌کرد. اگه بعداً یه فرم دیگه هم ساختید که کاربر رو به یه دامنه
بیرونی (نه خود سایت) می‌فرسته، همین `data-turbo="false"` رو روش بذارید.

### حس SPA بدون بازنویسی با React/Vue

چون همه‌چیز با Blade و رندر سمت سرور نوشته شده (که برای سئو حیاتیه)، برای این‌که
ناوبری بین صفحات حس یه اپلیکیشن تک‌صفحه‌ای (SPA) رو بده — یعنی صفحه هیچ‌وقت
کامل سفید نشه و رفرش نشه — از **Turbo (Hotwire)** استفاده شده. فقط با یه خط
اسکریپت (از CDN، بدون نیاز به npm/build) تو `layouts/app.blade.php` و
`layouts/panel.blade.php`، Turbo خودکار همه لینک‌ها و فرم‌ها رو به ناوبری
AJAX‌محور تبدیل می‌کنه:

- کلیک رو لینک‌ها → صفحه با fetch لود می‌شه و فقط `<body>` عوض می‌شه، بدون فلاش سفید
- ارسال فرم‌ها (حتی آپلود فایل) → از طریق همون مکانیزم، بدون رفرش کامل
- ریدایرکت به دامنه بیرونی (مثل درگاه زرین‌پال) → خودش تشخیص می‌ده و به‌صورت خودکار navigation کامل مرورگر انجام می‌ده (رفتار پیش‌فرض و درست Turbo)
- اسکرول و وضعیت صفحه هم حفظ می‌شه، دقیقاً مثل SPA

**نکته مهم برای توسعه‌ی بعدی:** چون Turbo فقط `<body>` رو عوض می‌کنه نه کل
`document` رو، هر اسکریپت جدیدی که می‌نویسید باید یکی از این دو الگو رو رعایت
کنه، وگرنه بعد از اولین ناوبری Turbo کار نمی‌کنه:

```js
// ✅ درست — چون document.addEventListener هیچ‌وقت با Turbo پاک نمی‌شه
document.addEventListener('submit', function (e) {
  const form = e.target.closest('.my-form-class');
  if (!form) return;
  // ...
});

// ✅ درست — برای بستن دوباره‌ی event listener روی المنت‌های تازه بعد از هر ناوبری
document.addEventListener('turbo:load', function () {
  const el = document.getElementById('my-element');
  if (!el || el.dataset.bound) return;
  el.dataset.bound = '1';
  el.addEventListener('input', function () { /* ... */ });
});

// ❌ غلط — فقط اولین بار که کاربر وارد سایت می‌شه اجرا می‌شه، بار دوم با Turbo کار نمی‌کنه
document.getElementById('my-element').addEventListener('input', ...);
```

این الگو همین الان تو فرم افزودن محصول (جداکننده هزارگان قیمت) و فرم‌های تأیید
واریز تسویه‌حساب (پنل ادمین) پیاده‌سازی شده — می‌تونید عیناً همون‌ها رو الگو بگیرید.

تمام صفحات ویترین سایت + هر سه پنل به‌صورت Blade واقعی (نه موکاپ استاتیک)
پیاده‌سازی شده و مستقیماً از کنترلرها دیتا می‌گیرند:

**ویترین عمومی:** خانه، صفحه دسته‌بندی (با فیلتر و صفحه‌بندی)، صفحه غرفه با محصولاتش، صفحه تکی محصول

**پنل مشتری:** تسویه‌حساب/پرداخت (زرین‌پال)، لیست سفارش‌ها، جزئیات سفارش با پیگیری هر مرسوله (چون هر غرفه جدا ارسال می‌کند)

**پنل غرفه‌دار:** داشبورد، لیست/افزودن محصول، لیست/جزئیات سفارش با ثبت کد رهگیری پستی، تاریخچه تسویه‌حساب

**پنل ادمین:** داشبورد کامل، تأیید/رد/تعلیق غرفه + تنظیم کمیسیون هر غرفه، مدیریت درخت دسته‌بندی، ساخت دسته تسویه‌حساب و ثبت واریز

فایل استایل مشترک (`resources/css/app.css`) هم داخل `public/css/app.css` کپی شده تا
بدون نیاز به Vite/npm build، مستقیم قابل استفاده باشه. اگر بعداً خواستید Tailwind
یا فرآیند build اضافه کنید، کافیه لینک `<link>` توی لایوت‌ها رو با `@vite(...)` عوض کنید.

## چیزهایی که هنوز باید اضافه شود

- فراموشی رمز عبور و تأیید ایمیل (Password Reset / Email Verification) — ساده‌ترین راه: نصب `laravel/breeze` و ادغام فقط همین دو بخش
- اعلان ایمیلی (پیامک کامل شد؛ ایمیل هنوز نه) — چون اکثر خریداران ایرانی موبایل رو چک می‌کنن نه ایمیل، اولویتش پایین‌تر بود
- فلگ `is_shippable` روی دسته‌بندی برای حذف مرحله ارسال از دسته‌های غیرفیزیکی مثل املاک (توضیح کامل در بخش «حمل‌ونقل سراسری»)
- نرخ‌های واقعی پست/تیپاکس به‌جای اعداد فرضی فعلی در `ShippingService`
- ثبت تحویل نهایی سفارش توسط مشتری (الان فقط تا «ارسال‌شده» پیش می‌ره؛ تأیید «تحویل گرفتم» توسط مشتری یا اسکن پیک هنوز نیست)
- سیستم امتیاز و نظرات برای غرفه‌ها (تو موکاپ بود ولی جدول/منطقش هنوز نیست)
- صفحات حقوقی: حریم خصوصی، قوانین و مقررات، درباره ما — هم برای اعتماد کاربر هم برای سئو (E-E-A-T گوگل)
- Rate limiting جدی‌تر روی مسیرهای OTP (الان فقط یک محدودیت ساده ۶۰ ثانیه‌ای هست)
- تاریخ‌ها همه‌جا میلادی نمایش داده می‌شن؛ برای یک سایت ایرانی بهتره با یک پکیج جلالی (مثل `hekmatinasser/verta`) به شمسی تبدیل بشن

## سئو — برای رتبه بالا تو گوگل

این بخش‌ها آماده و پیاده‌سازی‌شده:

- **عنوان و توضیحات اختصاصی هر صفحه** — هر صفحه (خانه، دسته‌بندی، غرفه، محصول) از `@section('title')` و `@section('meta_description')` خودش استفاده می‌کنه، نه یه متن ثابت تکراری.
- **Canonical URL** روی هر صفحه، خودکار.
- **Open Graph + Twitter Card** — برای وقتی لینک تو تلگرام/واتساپ/توییتر شیر می‌شه، عکس و عنوان درست نشون داده بشه.
- **hreflang** برای نسخه فارسی/انگلیسی (چون سایت دوزبانه‌ست).
- **داده ساختاریافته Schema.org (JSON-LD):**
  - `Organization` روی همه صفحات
  - `WebSite` + `SearchAction` روی خانه (برای Sitelinks Search Box تو نتایج گوگل)
  - `Product` کامل (قیمت، موجودی، برند=غرفه) روی صفحه محصول — **نکته مهم که اصلاح شد:** واحد پول تو schema باید کد رسمی ISO 4217 باشه (`IRR` = ریال)، نه کدهای غیررسمی مثل `IRT`؛ چون قیمت‌ها تو سایت به تومانه، موقع تولید schema خودکار ×۱۰ می‌شه تا به ریال درست تبدیل بشه — با کد اشتباه قبلی، گوگل کل Rich Snippet قیمت رو رد می‌کرد.
  - `BreadcrumbList` روی دسته‌بندی/غرفه/محصول
- **نقشه‌سایت پویا** (`/sitemap.xml`) — خودش با اضافه‌شدن دسته‌بندی/غرفه/محصول جدید به‌روز می‌شه (۱ ساعت کش می‌شه که فشار به دیتابیس نیاد).
- **robots.txt** — بخش‌های خصوصی (پنل‌ها، سبد خرید، لاگین) از ایندکس گوگل مستثنی شدن؛ فقط باید آدرس واقعی دامنه رو تو خط `Sitemap:` جایگزین `meydan.example.com` کنید.
- **جلوگیری از محتوای تکراری:** صفحات فیلترشده (دسته‌بندی با زیردسته انتخابی) و صفحات بعد از ۱ pagination، با `noindex, follow` علامت‌گذاری شدن.
- **جستجوی واقعی** (`/search?q=`) — قبلاً فرم جستجوی صفحه اصلی به هیچ کوئری وصل نبود؛ الان اضافه و وصل شد.

**کارهایی که برای رتبه بالا لازمه ولی داخل کد قابل انجام نیست:**
- ثبت سایت در Google Search Console + ارسال `sitemap.xml`
- گرفتن SSL (HTTPS) — گوگل به سایت بدون HTTPS رتبه پایین‌تر می‌ده
- تولید محتوای متنی واقعی (توضیحات کامل دسته‌بندی‌ها، وبلاگ) — کاتالوگ خالی بدون محتوا رتبه کمتری می‌گیره
- بک‌لینک و اعتبار دامنه — هیچ کدی جایگزینش نمی‌شه

## تاریخ شمسی و فرمت قیمت

**تاریخ‌ها:** همه‌جای سایت (تاریخ سفارش، تاریخ ثبت غرفه، دوره تسویه‌حساب، شماره
سفارش) الان به شمسی نمایش داده می‌شه — بدون نیاز به نصب هیچ پکیج جانبی. یه
کلاس سبک (`App\Support\Jalali`) الگوریتم استاندارد تبدیل میلادی به شمسی رو پیاده
کرده، و یه تابع سراسری `jdate($date, $format)` هم برای راحتی تو ویوها اضافه شده:

```php
jdate($order->created_at)                 // ۱۴۰۴/۰۶/۱۴
jdate($order->created_at, 'Y/m/d H:i')    // ۱۴۰۴/۰۶/۱۴ ۱۰:۳۲
jdate($booth->approved_at, 'F Y')         // شهریور ۱۴۰۴
```

عبارت‌های نسبی مثل «۲ روز پیش» هم با `->locale('fa')->diffForHumans()` (که خود
Carbon پشتیبانی می‌کنه، نیازی به پکیج اضافه نداره) به فارسی نمایش داده می‌شن.

**محدودیت شناخته‌شده:** ورودی‌های تاریخ تو فرم‌ها (مثل انتخاب بازه تسویه‌حساب تو
پنل ادمین) همچنان از `<input type="date">` استاندارد HTML استفاده می‌کنن که
مرورگر با تقویم میلادی نشون می‌ده — چون مرورگرها از تقویم شمسی پشتیبانی نمی‌کنن.
برای تقویم شمسی واقعی تو فرم‌ها باید یه دیت‌پیکر جاوااسکریپت جدا (مثل
persian-datepicker) اضافه کنید.

**قیمت‌ها:** همه‌جا که قیمت *نمایش* داده می‌شه، از `number_format()` استفاده
شده (جداکننده هزارگان با کاما) + پسوند «تومان» — این از قبل همه‌جا رعایت شده بود.
تنها جایی که واقعاً کم داشت، فرم **افزودن محصول** (پنل غرفه‌دار) بود؛ چون ورودی
قیمت از نوع `number` بود و مرورگر جداکننده هزارگان نشون نمی‌ده. الان به یه فیلد
متنی با جداکننده زنده تبدیل شده — یعنی غرفه‌دار تایپ می‌کنه `1850000` و بلافاصله
رو صفحه می‌شه `۱,۸۵۰,۰۰۰`، ولی چیزی که واقعاً به سرور ارسال می‌شه همون عدد خامه.

## داده نمونه (Seeder) — برای تست فوری

با `php artisan db:seed` این‌ها ساخته می‌شود:
- ۱ حساب ادمین: `admin@meydan.test` / `password`
- ۶ دسته‌بندی اصلی + ۱۳ زیردسته (همون ساختاری که تو موکاپ‌ها دیدید)
- ۸ غرفه تأییدشده با حساب غرفه‌دار جدا برای هرکدوم (`vendor1@meydan.test` تا `vendor8@meydan.test` / `password`)
- حدود ۳۰ محصول واقعی پخش‌شده بین غرفه‌ها
- ۱ مشتری نمونه با آدرس ثبت‌شده برای تست کامل جریان خرید: `customer@meydan.test` / `password`

بعد از seed کردن، همه صفحات (خانه، دسته‌بندی، غرفه، پنل‌ها) با دیتای واقعی پر می‌شن، نه خالی.
- Seeder برای داده نمونه (چند دسته‌بندی، غرفه، محصول) — الان فقط یک حساب ادمین پیش‌فرض ساخته می‌شود، برای دیدن صفحات با دیتای واقعی به داده بیشتری نیاز دارید

